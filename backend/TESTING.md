# Проверка системы опросов

Этот файл — точка входа для тестировщика. Все команды выполняются из `backend`. Основные проверки выполняются с PostgreSQL в Docker; SQLite не проверяет конкурентные блокировки строк.

## Подготовка стенда

1. Настройте `.env` по `.env.example`, если он ещё не создан. Для локальной проверки используйте `DJANGO_DEBUG=1` и `COOKIE_SECURE=0`.
2. Запустите `docker compose -p codex-polls-er4 up -d --build`.
3. Проверьте `http://localhost:18083/api/health`: ожидается `200` и `{"status":"ok"}`.
4. Создайте демонстрационные данные:

```powershell
docker compose -p codex-polls-er4 exec backend python manage.py seed_demo
```

Команда работает только при `DJANGO_DEBUG=1`. Она не очищает базу, не сбрасывает существующие пароли и не возвращает изменённые опросы в исходное состояние. Повторный запуск не дублирует неизменённые демонстрационные записи. Для собственной проверки создавайте отдельные опросы, чтобы не менять общие примеры коллег.

### Учётные записи

Первоначальный пароль всех пяти демонстрационных пользователей: **`Demo-Polls-2026!`**. Для другого пароля при первом создании передайте `seed_demo --password 'ВашПароль'`. Это пароль только локальных демонстрационных аккаунтов.

| Почта | Роль и назначение |
| --- | --- |
| `demo.owner@example.test` | Автор демонстрационных опросов |
| `demo.participant@example.test` | Участник с уже сохранёнными ответами |
| `demo.moderator@example.test` | Модератор для жалоб и предупреждений |
| `demo.admin@example.test` | Администратор для ролей и блокировок |
| `demo.banned@example.test` | Заблокированный пользователь; вход должен вернуть `401` |

### Начальные опросы

| Код | Состояние при первом создании | Для чего использовать |
| --- | --- | --- |
| `DEMO0001` | Активный, анонимный, без перепрохождения | Вопросы всех трёх типов, результаты, комментарии и лайки |
| `DEMO0002` | Активный, для зарегистрированных, с перепрохождением | Доступ по токену, замена ответов, список участников у автора |
| `DEMO0003` | Черновик | Проверка недоступности чужого черновика и конструктора |
| `DEMO0004` | Завершённый | Запрет новых голосов и комментариев |
| `DEMO0005` | Активный, доступ по ссылке | Отсутствие в каталоге, доступ по коду, жалоба для модерации |
| `DEMO0006` | Публикация через 10 минут | Работа планировщика; после времени публикации станет активным |

У участника есть ответы в `DEMO0001`, `DEMO0002`, `DEMO0004`. У автора ещё нет собственных ответов. Не подставляйте числовые `id` из чужой базы: сначала получите опрос через API.

## Автоматические проверки

В PowerShell можно запустить все проверки одной командой:

```powershell
./scripts/check.ps1
```

Скрипт проверяет конфигурацию Django, отсутствие забытых миграций, Ruff, форматирование, OpenAPI и весь набор тестов. Он останавливается при первой ошибке и возвращает ненулевой код. Контейнеры должны быть запущены и пересобраны после изменения исходников.

Отдельные наборы:

```powershell
docker compose -p codex-polls-er4 exec backend python manage.py test core.tests.test_api --verbosity 2
docker compose -p codex-polls-er4 exec backend python manage.py test core.tests.test_realtime --verbosity 2
docker compose -p codex-polls-er4 exec backend python manage.py test core.tests.test_concurrency --verbosity 2
docker compose -p codex-polls-er4 exec backend python manage.py test core.tests.test_handoff --verbosity 2
```

Тесты создают отдельную базу `test_polls` и удаляют её после завершения. Демо-данные в рабочей базе не изменяются. Не запускайте два полных прогона одновременно против одного PostgreSQL: они используют одно имя тестовой базы. Для параллельной работы поднимайте отдельные Compose-проекты с разными `API_PORT`.

В наборе для передачи проекта проверяются неполное редактирование вложенных вопросов, привязка ошибок к полям, CORS, описание прав в OpenAPI и повторяемость демо-данных. Упрощённый хешер пароля применяется только в тестах для скорости; обычное приложение использует штатный хешер Django.

## Проверка в Postman

Импортируйте [коллекцию запросов](postman/polls.postman_collection.json). В переменной коллекции `baseUrl` указан `http://localhost:18083/api`; при необходимости измените порт. Сначала выполните `seed_demo`.

Collection Runner выполняет отдельный сценарий: вход автора → создание опроса → публикация → вход участника → голосование → получение результатов → ожидаемый конфликт повторного голоса → вход автора → экспорт → завершение → удаление созданного опроса. Токены, код опроса и идентификаторы ответов подставляются автоматически. Успешный прогон удаляет только опрос, который создал сам. При прерванном прогоне созданный опрос останется в профиле демо-автора.

Токены хранятся в переменных коллекции во время прогона. Перед передачей экспортированной коллекции очищайте `access` и `refresh`. В сохранённом в проекте файле эти переменные пустые.

## Ручные сценарии

| Проверка | Действие | Ожидаемый результат |
| --- | --- | --- |
| Регистрация | Создать пользователя с новой почтой и никнеймом | `201`, пара токенов и профиль |
| Уникальность | Повторить почту или никнейм с другим регистром | `409` |
| Обновление сессии | Обновить refresh, затем повторить старый refresh | Сначала `200`, затем `401` |
| Выход | Выйти и вызвать `/users/me` с прежним access | `204`, затем `401` |
| Профиль другого пользователя | Открыть `/users/{id}` | Нет почты, пароля или токенов |
| Черновик | Открыть `DEMO0003` как участник | `403`; автор может открыть |
| Ошибка конструктора | Отправить PATCH с вопросом без `text`, `type` или текста варианта | `400` с ошибкой в `questions`, прежний опрос сохранён |
| Гостевое голосование | Пройти анонимный опрос в новом браузерном профиле | `200`, HttpOnly-cookie; результаты доступны этому браузеру |
| Повторный голос | Повторить голос в опросе без перепрохождения | `409`, число прохождений не меняется |
| Перепрохождение | Изменить ответы участника в `DEMO0002` | `200`, прежние ответы заменены, число прохождений не увеличено |
| Чужой вариант | Передать `option_id` из другого вопроса | `400`, голос не записан |
| Множественный выбор | Выбрать больше `max_choices` или повторить один вариант | `400` |
| Закрытый доступ | Открыть `DEMO0002` гостем | `401` |
| Анонимность | Запросить `/voters` для `DEMO0001` даже с токеном автора | `403`; экспорт не раскрывает участников |
| Видимость | Искать `DEMO0005` в каталоге | В каталоге его нет; по прямому коду открывается |
| Завершение | Отправить голос или новый комментарий в `DEMO0004` | `403` |
| Комментарии | Ответить на комментарий другого опроса через `parent_id` | `404`; запись не создаётся |
| Лайк | Лайкнуть свой комментарий; дважды лайкнуть чужой | Свой — `400`; чужой учитывается один раз |
| Модерация | Выдать три предупреждения новому тестовому пользователю | Автоблокировка; сессии отозваны |
| Разблокировка | Разблокировать и выдать одно новое предупреждение | Счётчик после разблокировки равен 1 |
| Права | Вызвать `/admin/users` обычным пользователем | `403` |
| WebSocket | Подключиться без участия; затем после голосования | Сначала доступ отклонён, после голоса приходят события |
| Отзыв WebSocket | Завершить сессию подключённого пользователя | Закрытие перед следующим событием или в течение 10 секунд |
| Экспорт | Скачать CSV, XLSX и PDF как автор | Файлы открываются, кириллица читается |

## Как оформить найденную ошибку

Укажите краткое название, роль пользователя, код опроса, метод и путь API, тело запроса без паролей и токенов, ожидаемый и фактический статус/ответ, шаги воспроизведения. Для WebSocket добавьте тип события и код закрытия.

Логи проекта:

```powershell
docker compose -p codex-polls-er4 logs --tail 100 backend scheduler
```

При `429` учитывайте заголовок `Retry-After`: вход, регистрация и refresh имеют общий лимит 15 запросов в минуту на IP. Перезапуск API не должен использоваться как способ исправить бизнес-ошибку; сначала сохраните запрос и ответ.

## Что проверять совместно с фронтендом

Автотесты бэкенда не подтверждают работу ещё не подключённого интерфейса. После интеграции отдельно проверьте cookie гостя в браузере, обновление токенов при параллельных запросах, обработку `401`/`403`/`409`, сбор дерева комментариев, загрузку аватара, скачивание файлов и восстановление WebSocket. Мобильная вёрстка, доступность интерфейса и пользовательские сценарии проверяются на готовом фронтенде.
