# Доработка бэкенда

## Рабочая папка и запуск

Основные исходники находятся в `backend` текущего проекта. Используйте команды из [README](README.md). Проект Compose во всех инструкциях называется `codex-polls-er4`: одинаковое имя сохраняет доступ к одним Docker-томам при смене папки исходников. Для отдельного стенда задайте другое имя `-p` и свободный `API_PORT`.

Образ содержит копию кода. После изменения Python-файлов выполняйте `docker compose -p codex-polls-er4 up -d --build`; простой перезапуск не обновит исходники внутри образа.

## Где менять поведение

| Изменение | Файлы |
| --- | --- |
| Поля, связи и ограничения | `core/models.py`, `core/migrations/` |
| Входные поля и структура ответа | `core/serializers.py` |
| Бизнес-правило и транзакция | `core/services.py` |
| HTTP-операция и проверка прав | `core/views.py`, `config/urls.py` |
| JWT и сессии | `core/auth.py` |
| События результатов | `core/consumers.py`, `broadcast_after_commit` |
| Экспорт файлов | `core/exports.py` |
| Планировщик | `core/management/commands/poll_scheduler.py` |
| Демонстрационные данные | `core/management/commands/seed_demo.py` |
| Общие схемы ошибок OpenAPI | `core/schema.py` |

`views.py` сейчас объединяет несколько предметных областей. При существенном росте API его можно разделить на модули пользователей, опросов и модерации, сохранив пути и контракты. Для небольшого исправления такое разделение не требуется.

## Порядок изменения API

1. Определите входные данные, ответ и права доступа. Уточните совместимость с разработчиком фронтенда, если меняются имена полей или форматы.
2. Добавьте или измените сериализатор. Вложенные вопросы при PATCH заменяются целиком, поэтому каждый переданный вопрос обязан содержать обязательные поля.
3. Реализуйте бизнес-правило. Счётчики голосов и лайков, ротация токенов и переходы статусов должны сохранять транзакции и блокировки строк.
4. Добавьте HTTP-операцию и описание `extend_schema`. Для обязательного входа задайте `IsAuthenticated`, включая методы классов со смешанным публичным и приватным доступом.
5. Добавьте регрессионный тест на наблюдаемое поведение, включая права доступа и отрицательные сценарии. Для гонок используйте PostgreSQL и `TransactionTestCase`; закрывайте соединения рабочих потоков.
6. Запустите `./scripts/check.ps1` и обновите сохранённый OpenAPI, если изменился контракт.
7. Обновите [FRONTEND.md](FRONTEND.md), [TESTING.md](TESTING.md) и коллекцию запросов, если изменение их затрагивает.

## Миграции

После изменения моделей создайте миграцию. Чтобы она сразу появилась на компьютере, а не только внутри контейнера:

```powershell
docker compose -p codex-polls-er4 run --rm --no-deps -v "${PWD}:/app" backend python manage.py makemigrations core
docker compose -p codex-polls-er4 up -d --build
```

Команды выполняются из `backend`, сервисы БД уже должны работать. Существующие миграции, которые уже применили коллеги, не переписывайте. Проверка `makemigrations --check --dry-run` обнаруживает изменения моделей без миграции.

## Актуальная схема OpenAPI

После пересборки изменённого приложения:

```powershell
docker compose -p codex-polls-er4 exec backend python manage.py spectacular --validate --fail-on-warn --file /tmp/openapi.yaml
docker compose -p codex-polls-er4 cp backend:/tmp/openapi.yaml ./openapi.yaml
```

Этот файл можно импортировать в Postman и использовать для генерации типов клиента. `my_answers` описан отдельной схемой с `question_id` и `option_ids`; ответы ошибок также включены в спецификацию. Runtime-описание доступно через `/api/schema`.

## Форматирование

В Docker можно проверить стиль без изменения файлов командой `python -m ruff format --check .`. Чтобы применить форматирование к исходникам на компьютере:

```powershell
docker compose -p codex-polls-er4 run --rm --no-deps -v "${PWD}:/app" backend python -m ruff format .
```

## Данные и границы проверок

Не изменяйте общие демо-аккаунты для личных экспериментов: создайте пользователя через регистрацию и отдельный опрос. Автотесты работают в отдельной базе; `seed_demo` добавляет данные в рабочую базу только в режиме разработки. Запуск `down -v` удаляет локальные тома и не нужен для обычной доработки.

Коммиты и работа с удалённым репозиторием выполняются по правилам команды. Данные `.env`, токены, файлы базы и пользовательские загрузки не включаются в исходники.
